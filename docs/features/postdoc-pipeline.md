# CV-first Opportunity Pipeline Handoff

## Opportunity shelving (schema 14)

- Recruitment availability, material completeness and workflow shelving are independent. `opportunities.shelved_at` persists a whole-opportunity decision even without a contact; no files or history are deleted.
- Discovery includes only unshelved opportunities with no contacts or an unshelved pending contact. Shelving one contact does not suppress other pending contacts. All still includes shelved records; fully archived opportunities remain hidden.
- The shelved tab groups opportunities with any shelved contacts or an opportunity-level decision, counted once before pagination (`shelvedTotal`). Mixed cards show only their shelved contacts in this tab. Other stage tabs remain contact-based.
- Whole-opportunity shelf/restore updates contacts transactionally, preserving their underlying stage and submission flag. Restore explicitly restores all contacts. Manually restoring one contact clears the opportunity-level hold but leaves other contacts shelved.
- Saving an inbound reply uses the same single-contact restoration semantics in one transaction: the replying contact and its opportunity are restored, other contacts retain their holds. Detail and importer select the latest reply with the same timestamp/row-order tie-breaker.
- Search cannot clear the decision; enqueue/retry, contact import and material publication check shelving. Cards offer secondary shelf/restore controls, explicit confirmation, errors and immediate refresh.

## Scope

Generic-user onboarding, durable Postdoc discoveries, material completion and continuation. This is one pipeline within the existing scheduler, not a new agent framework. Gmail, provider transport and Internship-specific behavior remain separately owned.

## Runtime flow

1. Upload a CV and optionally describe a goal; connection setup and background details are collapsible. Source CV text is local evidence. Model processing happens only when an Agent task is started.
2. Import retains the original/copy, produces sourceText and a source-profile version. Mac has bundled local OCR; Windows currently needs text-layer PDFs. Extraction errors leave the previous active profile intact.
3. Enqueue snapshots profile files. Discovery reads the CV background, verifies primary sources and writes search-results.json without requiring materials.
4. Import saves discoveries first. No matches is a normal reviewable outcome. A missing supervisor may use a real official portal/office target; never fabricate a person or email.
5. Pending materials get up to two targeted completion turns with the same thread. Local errors become structured pendingMaterials items, not Chinese-message-based routing. Non-search workflows retain their own paths.
6. A complete version directory is rendered once and published transactionally. Failed renders never install partial artifact pointers. Existing artifact packages are protected; use explicit revisions to change them.
7. The task ends needs_review, including partial outcomes. Retry imports saved output first and works on pending items. Same-provider changes preserve the thread; a provider change starts a new provider-compatible thread but retains workspace evidence. Edited retry instructions are shared by the message, contract and revision history. Revision retries preserve the original trusted base and input, including when the model or prompt changes. Missing/invalid revision output and CV layout failures share at most two targeted repair turns; identity, base-hash, ownership, database and permission errors cannot trigger repair or silently reset a baseline.

## Persistence and contracts

- Contact details offer explicit manual replied/follow-up/shelved/ready decisions through the existing set_contact_status API, separate from entering reply evidence. Confirmation does not invent reply text, send mail or change other contacts. Shelving is reversible and retains records.
- Incomplete opportunity cards open a continuation composer with optional instructions, a 1–5 contact limit and model selection. It enqueues an existing full_search job with payload.opportunityId and the opportunity snapshot; targetId remains absent because that field expects a contact. This is a new scoped task, not a resumed historical thread. Normal retry within its job keeps the existing retry semantics. Continuations are deduplicated by opportunity ID, including pre-existing jobs with query-based keys. DiscoveredOpportunity.latestJob is a nullable JobSummary projection loaded from existing native_jobs payloads with an indexed lookup, prioritizing active jobs. Cards display saved progress and reuse JobCard for details, cancellation and edited retry; no page-local-only task association or new endpoint is needed. Job history is excluded from snapshots sent to the model.
- Identity checks require the same institution plus either the same canonical source URL or a matching saved official ID on the same host; title alone never authorizes a merge. Ambiguous opportunity matches return identity_needs_review without merging records. Users may explicitly confirm a specific official source URL in the continuation composer; the Agent must still provide primary-source evidence. Fresh verification synchronizes category, title, organization, department, country/region, deadline/source and summary. Blank or unknown values retain old metadata; older verification timestamps cannot replace newer metadata. Target titles/organizations are synchronized only when still inherited from the previous opportunity value, preserving custom contact text and progress.
- Contact identity combines names, email and personal-page evidence for both target and PI lookup. Verified email corrections can retain identity, but conflicting people are reviewed before contact/material writes, including contacts spread across duplicate opportunity entries in one search output. Saved opportunity/source evidence may remain; ambiguous contacts never overwrite each other's email, material pointers or history.
- Schema 13 adds contact_targets_v2.status_version and a trigger incrementing it on every status/shelving update, including change-then-restore. Reply enqueue captures the version server-side; import uses a transaction-protected comparison before applying a recommendation. Newer user edits and old jobs without a snapshot retain current status; the job message asks for manual confirmation. Migration uses the existing pre-upgrade SQLite backup, is idempotent, and retains prior data.
- Reply results use immutable `generated/contact-targets/<target>/reply-history/<uuid>` files and the existing revision/history tables. Current draft pointers and guarded status updates commit together. A newer reply or a newer reply task (creation time with row-order tie-breaking) makes an older result history-only; it cannot change current drafts/status or import referrals. A rerun of the current task for the current reply can publish a new draft version while retaining prior bytes. Legacy jobs without reply identity cannot replace existing drafts. “编辑与修订” exposes each result, including unpublished historical candidates.
- Enqueue and retry share the same active-task check, including opportunity IDs in legacy payloads even when active keys differ or are absent. Rejection leaves the original thread and job state unchanged. Source URL matches never override conflicting official IDs: scoped continuation requests manual review, independent searches retain distinct postings, and ambiguous shared URLs without an ID are not merged arbitrarily. Verified IDs learned on an existing URL are retained for future conflict checks.
- Discovery rejects stale verification timestamps both before material preparation and inside the contact write transaction. Older results cannot roll back contact email/source/score or add contacts after a newer verification; `stale_results_ignored` distinguishes this from finding no matches. Source evidence can remain as history. No additional schema migration is required for these guards.
- Completeness is checked against CV PDF/data/source, the requested-language email/fit/contact brief, and a checklist, including actual file presence. An unrelated report is not a complete package. Publication only adds missing files/checklist items, preserving manual content and existing pointers. Missing files can receive new version paths; original files are not overwritten. CV regeneration uses existing structured data when available, checks for concurrent CV edits before publishing, and requests manual review if partial legacy CV files have no structured source. Completed contacts do not consume the missing-material quota. Target details show material_error.
- Native schema 12: contact_targets_v2.material_status (pending/ready), material_error. Existing records default ready; no legacy file deletion.
- “已发现机会” includes opportunities without active contacts or with any active contact whose material_status is pending; once every active contact is ready, the opportunity leaves this tab. “全部” includes both incomplete and completed opportunities, regardless of contact progress. Both count opportunities (not contacts), support search/pagination, and refresh every 10 seconds while the Postdoc page is visible. The backend filters before pagination and returns independent pendingTotal/overallTotal badges, unaffected by search. Multiple active contacts link from one card; records with only archived contacts remain hidden. No schema change is required.
- Every Postdoc state has an independent category filter: advertised / prospective / uncertain. Classification is owned by db.rs::POSTDOC_CATEGORY, shared by opportunity and contact queries; explicit prospect kinds (including legacy cold_outreach and fellowship_host) override stale open statuses. Unknown kinds stay uncertain rather than being inferred from missing deadlines. State badges include all types; category filtering happens before counts and pagination. Internship queries are unchanged.
- Advertised lists sort valid ISO deadlines from nearest upcoming date, followed by unknown/text deadlines, then expired/closed records. Prospects sort by fit score. Dashboard shows the first three of each primary category using those same queries, with links carrying the category through App hash routes; uncertain records have a separate review entry. These are read-only views and never rewrite legacy classification or contact stages.
- Dashboard presentation is scoped by Overview / Postdoc / Internship tabs. Overview contains only two independent summaries and nearest-known-deadline hints; no combined opportunity list or merged region chart. Postdoc owns prospect/advertised lists, material/reply alerts and contact regions. Internship owns submission progress, application regions and the first four records ordered by deadline across submission stages. Its dashboard ordering is separate from the existing application-list ordering. Counts are labelled as opportunities, people or application records to avoid conflating units. Shared CV/provider configuration is unchanged.
- Job result: businessResult.outcome = ready/materials_pending/no_matches/sources_need_review/identity_needs_review/stale_results_ignored; imported, pendingMaterials, warnings and summary are explicit. Reply results include draftsApplied and statusApplied separately.
- Search schema v1 remains readable. materials is optional during discovery; fitScores is the new six-dimension numeric contract. Old reports use the legacy reader.
- Opportunities use availability and optional eligibilityStatus. Legacy missing availability resolves uncertain, not automatically open.
- New source profiles contain source.file/textFile/sha256/provenance and sourceText. They are interpreted by the model at task time; this is not external fact verification.
- Version directories live under generated/contact-targets/<target>/versions/<uuid>. Original inputs and historical materials are retained.
- Sources and original CV remain local until a task sends relevant context to the selected model provider. No extra cloud OCR service or automatic email/submission is introduced.

## Debug checklist

- Postdoc pending-material contacts at `ready_to_contact` are excluded from the ready tab and dashboard ready count until their package is ready. Other contact stages remain visible; all opportunities remain in All. This prevents one incomplete contact from appearing as both discovered and ready.
- Pending contact details expose the associated original search task and unpublished target-owned CV candidate files, separate from official artifacts. CV/revision tabs offer original-task retry (which may repair other pending items in that batch) or scoped opportunity completion. Recovery does not require an already published CV; shelved contacts must be restored first. No automatic retry or approval occurs.

1. Check upload extraction and sourceText before diagnosing model behavior.
2. Inspect the job's saved profile snapshot, not only the current global profile.
3. Check discovery output and native_job_results before treating a failure as “no opportunities”.
4. Inspect material_status/material_error and pendingMaterials for per-target failures.
5. Check the unpublished version directory and Typst error if PDF validation fails.

## Three-batch hardening — 2026-09-06

This slice addresses R1–R6 in `docs/reviews/postdoc-workflow-audit-2026-09-06.md`. Internship feature gaps remain deferred. The existing scheduler and storage tables are retained; no framework, dependency or schema migration was added by this slice.

1. **Execution and publication:** a claimed job carries job/worker/attempt identity. `db::publication_transaction` reserves the SQLite writer and checks that identity, cancellation, deadline and lease before a task publishes. Startup/lease recovery preserves cancellation and live foreign claims; stale executors cannot finish a newer claim. CV, Cover Letter and text edits stage immutable UUID versions, validate current artifact paths/hashes and publish history plus pointers together. CV data/template/PDF and Cover Letter text/data/PDF commit as matching packages. Failed compilation, SQL publication or stale-base checks leave the current version and approval intact. Cancellation kills in-flight Typst compilation; already committed discoveries/history remain retained.
2. **Approval and profile consistency:** Gmail approval takes the exact preview path and SHA256 across the Rust/API/UI boundary. MIME uses captured approved bytes, not a later file reread. A deterministic local reservation prevents repeated identical POSTs; the returned remote draft ID is saved before GET verification. Verification failure shows “已创建 · 待核验”, and identical retries only verify the known ID. An uncertain POST stays blocked for manual Gmail checking; this slice does not add a resolve/release UI for unknown outcomes. Nothing sends email. Agent CV revision validates against its original task snapshot; a missing required snapshot is an explicit error. Manual generation freezes JSON policy inputs. CV upload validates both profile files first and uses a recoverable two-file journal; incomplete task snapshots are staged anew rather than inheriting stale optional files. Original sources/backups remain.
3. **Effective state and identity:** material readiness is recomputed from published files/checklist after manual generation, revisions and search outcomes, independently of contact/submission state. A small internal `material_requirements/und` artifact records package language; it is excluded from visible material lists. Legacy records without it use current onboarding language until a search establishes the package requirement. A late failed attempt does not demote a newer complete package. Search checks saved merged availability/deadline and rechecks at publication. The CV panel refreshes detail after generation and rejects stale preview responses. Postdoc URL identity preserves path/query case and trailing slash while normalizing host/tracking; no historical keys are bulk rewritten or old merges automatically split. Internship URL identity retains its previous normalization.
